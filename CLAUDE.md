# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A .NET 10 minimal API backend for managing employees: JWT auth (signup/login/logout with real server-side revocation), employee records, activity statistics, Swagger UI, and a SQL Server database that also logs every API call made against it. Single-project solution — no separate test project exists yet.

## Commands

```
dotnet build                                                        # from repo root or EmpoloyeeManagment/
dotnet run --project EmpoloyeeManagment                             # run the API (from repo root)
dotnet ef migrations add <Name> --project EmpoloyeeManagment         # add a migration
dotnet ef database update --project EmpoloyeeManagment               # apply migrations
```

Run from inside `EmpoloyeeManagment/` and drop `--project EmpoloyeeManagment`. The global `dotnet-ef` tool version must match the `Microsoft.EntityFrameworkCore.Design`/`Tools` package version (currently 10.0.9) — `dotnet tool update -g dotnet-ef` if migrations commands fail with a version mismatch.

To stand up the schema on a machine with no .NET tooling (an external SQL Server, a DBA-run deploy), use [`EmpoloyeeManagment/docs/database-setup.sql`](EmpoloyeeManagment/docs/database-setup.sql) — an idempotent script generated via `dotnet ef migrations script --idempotent`, covering all 8 migrations through `AddLeaveRequests`. It is a snapshot, not live-generated: regenerate it (same command, `--output EmpoloyeeManagment/docs/database-setup.sql`) whenever a new migration is added, or it will silently omit it. See README.md's "Setting up the database on another machine" for full usage. Role seeding (`Admin`/`Manager`/`Supervisor`/`Employee`) happens in `Program.cs` at app startup, not in this script.

Prerequisites: .NET 10 SDK, a local SQL Server instance (default instance or LocalDB) with the connection string in `appsettings.Development.json` (`ConnectionStrings:DefaultConnection`). After `dotnet run`, open `/swagger` (e.g. `http://localhost:5134/swagger` with the `http` launch profile) — use the "Authorize" button to paste a JWT obtained from `/api/auth/login` or `/api/auth/signup`.

There are no automated tests in this repo yet; verification is manual via Swagger (see `EmpoloyeeManagment/docs/Project_Startup_Plan.md` for the full walkthrough: signup → login → Authorize → create employee → list/detail → activate/deactivate → statistics → logout → confirm the old JWT now gets 401).

## Architecture

**Composition root**: `Program.cs` wires DI, the middleware pipeline, and endpoint mapping only — no business logic lives there. Each feature area's endpoints are mapped via a `Map*Endpoints(this IEndpointRouteBuilder)` extension method (`AuthEndpoints`, `EmployeeEndpoints`, `StatisticsEndpoints`, `UserEndpoints`, `TaskEndpoints`, `VisitEndpoints`, `ClientEndpoints`, `NotificationEndpoints`), each building its own `app.MapGroup("/api/...")` with `.RequireAuthorization()` applied once at the group level; some routes layer an additional named-policy `.RequireAuthorization("...")` on top of that at the route level — `EmployeeEndpoints`'s activate/deactivate use `AdminOnly`; `TaskEndpoints`'s assign/reassign/cancel/complete use `TaskAssigner` (Admin/Manager/Supervisor), and accept/reject use `EmployeeOnly`; `ClientEndpoints`'s group uses `TaskAssigner` (read access for Admin/Manager/Supervisor) with `POST` further restricted to the narrower `ClientManager` policy (Admin/Manager only, deliberately excluding Supervisor, who can view but not create clients) — see Role-based access control below. `TaskEndpoints` additionally does **row-level** (ownership-based) authorization inside its handlers — `GET /api/tasks`, `GET /api/tasks/{id}`, and the comment endpoints check `User.IsInRole(...)`/resolve the caller's linked `Employee` directly, since a policy can only gate an entire route, not filter which rows a caller may see or touch. An Employee may only see/act on tasks where they are the assignee; Admin/Manager/Supervisor see every task — there is no reporting-hierarchy/team model in this codebase, so "Supervisor sees their team's tasks" is implemented as "sees all tasks" (a documented superset, not a bug). `ClientEndpoints` does the same kind of row-level scoping, but the split is different: Admin/Manager see every client; a Supervisor sees only the one client that owns their `Employee.AssignedLocationId`. `StatisticsEndpoints`'s Supervisor-facing routes (the per-employee monthly rollup and the status-stats endpoint) do the same kind of row-level scoping too, but since there's no real team model to scope against, they define a Supervisor's "team" heuristically: the employees who are the assignee of a visit-linked task under the client the Supervisor is assigned to (the same client `ClientEndpoints.GetSupervisorAssignedClientIdAsync` resolves) — see `.squad/plans/dashboards/06-story-activity-dashboards-and-stats.md` Story Goal point 5 and Edge Cases for the full reasoning and known limitations. `NotificationEndpoints` is the first feature to do row-level scoping directly on the caller's raw Identity user id (`Notification.RecipientUserId`, compared against `ClaimTypes.NameIdentifier`) rather than resolving an `Employee` first — simpler than every other row-level endpoint here because a notification's ownership has nothing to do with the `Employee` table at all. `LeaveEndpoints`'s submit route (`POST /api/leaves`) uses a new `LeaveRequester` policy (Employee/Manager/Supervisor); its accept/reject/request-delay routes reuse the existing `TaskAssigner` policy, then add a row-level `CanActionLeaveRequest` check that compares the caller's role against the request's requester's *resolved* role (looked up via the `AspNetRoles`/`AspNetUserRoles` join, the same pattern `UserEndpoints.GetUsersAsync` and `StatisticsEndpoints.GetSupervisorTeamStatisticsAsync` use) on a strict linear rank (`Employee < Supervisor < Manager < Admin`) — not a team/location scope like `ClientEndpoints`/`StatisticsEndpoints`, since leave approval routing in the source spec is purely role-based.

**Auth is `AddIdentityCore`, not `AddIdentity`** — deliberately, since this is a pure bearer-token API with no browser sign-in surface; the full `AddIdentity` wires up cookie auth as a side effect (401s become redirects), which fights JWT-only auth. `.AddRoles<IdentityRole>()` is chained on top for role support (see below) — that only adds role-related DI services (`RoleManager<IdentityRole>`, role store wiring), not `AddIdentity`'s cookie behavior.

**Real server-side sign-out via security-stamp rotation**: JWTs carry a custom `securityStamp` claim captured at issue time (see `Services/TokenService.cs`). `JwtBearerEvents.OnTokenValidated` in `Program.cs` re-fetches the user's *current* stamp via `UserManager` on every authenticated request and fails auth if it doesn't match — this is the same mechanism cookie-based Identity auth uses internally (`SecurityStampValidator`), applied manually to bearer tokens. `POST /api/auth/logout` calls `UserManager.UpdateSecurityStampAsync`, which immediately invalidates *every* outstanding token for that user (not per-device revocation — a known v1 limitation). This trades some of JWT's normal statelessness for a DB read per request; accepted as fine at this scale.

**Signup is transactional across two tables**: `AuthEndpoints.SignupAsync` opens a `db.Database.BeginTransactionAsync()` before calling `UserManager.CreateAsync` (Identity writes through the same scoped `AppDbContext`, so it participates in the transaction) and then inserts a linked `Employee` row (`Employee.UserId` → the new user's Id) with `Status = Inactive`. Both writes commit or roll back together — an admin later activates the employee via `PATCH /api/employees/{id}/activate`. `POST /api/users` (Admin-only, `Endpoints/UserEndpoints.cs`) follows the identical transactional shape for admin-initiated user creation, deliberately duplicated rather than shared with `SignupAsync` since the two live in different endpoint files and the codebase has no cross-feature service-extraction convention yet.

**Role-based access control**: four fixed `IdentityRole`s (`Admin`, `Manager`, `Supervisor`, `Employee`, see `Models/Enums.cs`'s `Role` enum) are seeded idempotently on startup (`Program.cs`, right after `builder.Build()`), which also backfills any pre-existing user with no role to `Employee`. Every signup is auto-assigned `Employee`; `POST /api/users` can assign any of the four. The JWT carries the user's role(s) as `ClaimTypes.Role` claims (`Services/TokenService.cs`) — the framework's default role claim type, so `.RequireRole(...)`/`User.IsInRole(...)` need no extra `TokenValidationParameters` configuration. `Authorization/AdminAuthorizationHandler.cs` is a single `IAuthorizationHandler` that succeeds *any* pending authorization requirement for a user in the `Admin` role, which is what makes Admin override every other role check app-wide — not a rule repeated per endpoint. A user's role claims are only as fresh as their JWT: changing a role in the DB doesn't affect an already-issued token until it expires or the user logs back in (logout alone doesn't refresh it).

**API call logging happens in `Middleware/ApiLoggingMiddleware`, registered first in the pipeline** (before CORS/auth), so it wraps and times literally every request including ones that fail auth. Because middleware unwinds inside-out, by the time its `finally` block runs, inner auth middleware has already populated `context.User`, so the log row can include the user id even though logging middleware runs "before" auth. The `SaveChangesAsync` for the log write is caught and logged via `ILogger`, never rethrown — a logging failure must never turn a successful business response into a 500. This is a plain synchronous per-request insert (no queue/batching) — treat that as an intentional v1 choice, not an oversight, if you touch this file.

**Swagger uses the .NET 9/10 native OpenAPI generator, not classic Swashbuckle `AddSwaggerGen`**: `Microsoft.AspNetCore.OpenApi`'s `AddOpenApi()`/`MapOpenApi()` generates `/openapi/v1.json`; `Swashbuckle.AspNetCore.SwaggerUI` (UI-only package) renders it at `/swagger`. `OpenApi/BearerSecuritySchemeTransformer.cs` is a custom `IOpenApiDocumentTransformer` that adds the JWT bearer scheme to the generated document — this is what makes the UI's "Authorize" button work, since Swashbuckle's old `AddSecurityDefinition`/`IOperationFilter` model doesn't apply once Microsoft's generator owns the document.

**Data model** (`Data/AppDbContext.cs : IdentityDbContext<ApplicationUser>`): `ApplicationUser : IdentityUser` (Identity's stock user), `Employee` (links to `ApplicationUser` via nullable `UserId`; `Gender`/`Status`/`AttendanceStatus` enums; nullable `AssignedLocationId` FK → `Location`, `Restrict` delete — only meaningful for a `Supervisor`-role user, settable only via `POST /api/users`), `ApiCallLog`, `TaskItem` (assigned work item, FK `AssigneeId → Employee`, FK `RelatedVisitId → Visit` with a unique filtered index enforcing one task per visit), `TaskComment` (FK `TaskId → TaskItem`, `AuthorEmployeeId → Employee`), `Visit` (`DateTime`, `ClientId → Client`, `LocationId → Location`, both `Restrict` delete — no stored `Status`, always read live from its linked `TaskItem.Status`), `Client` (`Name`/`Email`/`Contact`), `Location` (`Name`/`Email`/`Contact`, FK `ClientId → Client`, `Cascade` delete — a client has many locations), `Notification` (`RecipientUserId → ApplicationUser`, `Restrict` delete; `Type` enum; `ReferenceId` a bare unconstrained int — a future leave request id, following the same deferred-FK shape `TaskItem.RelatedVisitId` used before `visits` added its FK), `LeaveRequest` (`RequesterId → Employee`, `ApproverEmployeeId` nullable `→ Employee` — both `Restrict` delete, the first entity in this codebase with two FKs to the same principal type; `Status` one of `Pending`/`Accepted`/`Rejected`/`DelayRequested`; `DecisionReason`/`RequestedDelayDate` nullable, set only once actioned). Enum values matter and are serialized as strings (`JsonStringEnumConverter` registered in `Program.cs`): `Gender { M, F }`, `EmployeeStatus { Active, Inactive }`, `AttendanceStatus { InOffice, Absent, OnVacation, OutOfOffice }`, `TaskItemStatus { New, InProgress, Rejected, Cancelled, Done }`, `NotificationType { LeaveRequestSubmitted, LeaveRequestAccepted, LeaveRequestRejected, LeaveRequestDelayRequested, TaskAssigned, VisitAssigned }`, `LeaveRequestStatus { Pending, Accepted, Rejected, DelayRequested }`. `Role { Admin, Manager, Supervisor, Employee }` is serialized the same way in DTOs but is **not** a persisted column anywhere — `IdentityDbContext<ApplicationUser>` already carries the full `AspNetRoles`/`AspNetUserRoles` schema regardless, so `Role` only exists at the API boundary and is converted to/from Identity's string role names (`nameof(Role.Admin)` ⇄ `IdentityRole.Name`).

**Tasks are named `TaskItem`/`TaskItemStatus`, never `Task`/`TaskStatus`** — `System.Threading.Tasks` is a project-wide global using (see `EmpoloyeeManagment.GlobalUsings.g.cs`), so `Task`/`TaskStatus` would collide with the BCL types every `async Task` method in this codebase already depends on.

**Task lifecycle and attendance**: `TaskEndpoints` (`Endpoints/TaskEndpoints.cs`) computes `TaskItem.Status` entirely server-side — it is never accepted as direct client input. `POST /api/tasks` creates `New` (validating `RelatedVisitId`, if given, both for existence and for not already being linked to another task); `accept`/`reject` (Employee-only, own task) move `New` → `InProgress`/`Rejected`; `cancel` (from `New`/`InProgress`) and `complete` (from `InProgress`) are Admin/Manager/Supervisor-only additions beyond the literal spec text, added because the status enum requires `Cancelled`/`Done` to be reachable states — `complete` works identically for visit-linked tasks now, since that **is** how a `Visit` reaches its "done" state (there is no independent way to complete a `Visit`). Reassigning (`PATCH /api/tasks/{id}`) resets `Status` to `New` and does **not** re-check the visit concurrency rule below for the new assignee (a documented gap — see `.squad/plans/visits/04-story-visit-tracking-and-status.md` Edge Cases). `Services/IEmployeeAttendanceService` recalculates `Employee.AttendanceStatus` (`InOffice`⇄`OutOfOffice`) whenever an `AttendanceRequired` task starts/stops being `InProgress` for its assignee, but only while the employee's current status is already `InOffice`/`OutOfOffice` (an `Absent`/`OnVacation` status set by some other process is left untouched) — built as a shared service so the visits feature could extend the same recalculation instead of duplicating it; in practice it needed **no changes at all**, since a visit's driving task is always created with `AttendanceRequired = true`. `TaskItem.RelatedVisitId` now has a real FK to `Visit` plus a unique filtered index (at most one task per visit) — `AcceptTaskAsync` additionally rejects (`400`) accepting a visit-linked task if its assignee already has another visit-linked task that's `InProgress` (accepted-and-not-yet-`Done`).

**Visits — fully shipped**: `VisitEndpoints` (`Endpoints/VisitEndpoints.cs`) implements `GET /api/visits`/`GET /api/visits/{id}` (same row-level visibility as tasks: Employee sees only visits whose linked task is assigned to them, Admin/Manager/Supervisor see all) and `POST /api/visits` (`TaskAssigner` policy). `Visit` has no stored `Status` column — every response reads it live via a join to the linked `TaskItem`. `CreateVisitAsync` validates the client and location exist, that the location belongs to the given client (`400` if not), that the assignee exists, and the same accepted-visit concurrency rule as `AcceptTaskAsync` (a duplicated `HasActiveAcceptedVisitAsync` helper — no shared service, per the codebase's no-cross-feature-service convention, Context item 6 in the story below), then creates the `Visit` and its driving `TaskItem` (`AttendanceRequired = true`, `Status = New`) in one transaction, mirroring `AuthEndpoints.SignupAsync`'s shape. See [`.squad/plans/visits/04-story-visit-tracking-and-status.md`](.squad/plans/visits/04-story-visit-tracking-and-status.md) task 6 for the original design (implemented essentially as written, once `clients` unblocked it).

**Leave requests — fully shipped**: `LeaveEndpoints` (`Endpoints/LeaveEndpoints.cs`) implements `POST/GET/PATCH/DELETE /api/leaves` (submit/list/detail/edit/delete) and `PATCH /api/leaves/{id}/accept|reject|request-delay`. `POST` uses a new `LeaveRequester` policy (Employee/Manager/Supervisor); the three action routes reuse the existing `TaskAssigner` policy, then add a manual, row-level `CanActionLeaveRequest` check that compares the caller's resolved role against the request's requester's resolved role on a strict linear rank (`Employee < Supervisor < Manager < Admin`) — this both implements the source spec's approver-routing table and, as an emergent property of requiring strict inequality, blocks self-approval and peer-approval without a separate check. Edit/delete (`PATCH`/`DELETE /api/leaves/{id}`) are requester-only and `Pending`-only, returning `403` (not `404`) for a non-owner, mirroring `TaskEndpoints`'s comment-ownership check rather than its task-ownership check. `LeaveEndpoints.CreateLeaveRequestAsync` calls `INotificationService.NotifyLeaveRequestSubmittedAsync`, with recipients resolved by `GetEligibleApproverUserIdsAsync` — every employee whose resolved role outranks the requester's, per the same rank table `CanActionLeaveRequest` uses for authorization (so a Manager's own submission notifies only Admins). `AcceptLeaveRequestAsync`/`RejectLeaveRequestAsync`/`RequestDelayAsync` each notify the requester with `LeaveRequestAccepted`/`Rejected`/`DelayRequested` respectively.

**Notifications — storage, reading, and every trigger now wired**: `NotificationEndpoints` implements `GET /api/notifications` (the caller's own rows, newest first) and `PATCH /api/notifications/{id}/read` (`404` for someone else's or a nonexistent notification). `Notification.ReferenceId` is still a bare, unconstrained `int` — deliberately mirroring how `TaskItem.RelatedVisitId` started before `visits` attached a real FK to it — now meaning a `LeaveRequest.Id`, `TaskItem.Id`, or `Visit.Id` depending on `Type`. `Services/INotificationService`/`NotificationService` expose one method per `NotificationType` member, all funneling through a shared private `CreateNotificationsAsync(type, referenceId, recipientUserIds)` helper (try/catch/log, never rethrown — a notification-creation failure must never turn a successful business response into a 500, same principle as `ApiLoggingMiddleware`). Beyond the leave-request notifications described above, `TaskEndpoints.CreateTaskAsync`/`ReassignTaskAsync` notify the (new) assignee with `TaskAssigned`, and `VisitEndpoints.CreateVisitAsync` notifies the assignee with `VisitAssigned` (deliberately not also firing `TaskAssigned` for the visit's auto-created driving task, since that task is an implementation detail from the recipient's point of view). This full wiring was added after the original `notifications` story shipped storage/reading only — the frontend's own `notifications` initiative needed real notifications to build and verify its UI against, and the user explicitly approved a one-time exception to extend this backend for that purpose. See [`.squad/plans/notifications/07-story-leave-request-notifications.md`](.squad/plans/notifications/07-story-leave-request-notifications.md)'s Addendum for the full account.

**CORS**: allowed origins are config-driven (`Cors:AllowedOrigins` in `appsettings.*.json`, currently `http://localhost:3000` for a Next.js client) and applied via a named `"NextJsClient"` policy with `AllowAnyHeader().AllowAnyMethod()` but no `AllowCredentials()` — auth is a bearer token in the `Authorization` header, not cookies, so credentialed CORS isn't needed.

**Secrets**: the JWT signing key in `appsettings.Development.json` is a locally-generated dev-only value checked in for convenience — move it to user-secrets or an environment variable before any deployment or before this leaves local dev.

## Known v1 gaps (not oversights — see README roadmap)

Employee update/delete and per-device token revocation (logout currently revokes all of a user's sessions at once) are deliberately out of scope for now. Role-based access control shipped (four fixed roles, admin user management via `/api/users`); changing an existing user's role after creation is still out of scope. Task assignment, accept/reject, cancel/complete, and comments shipped (`/api/tasks`), including a real FK + concurrency check for visit-linked tasks; task attachments and real reporting-hierarchy/team scoping for Supervisors (they see every task/visit, not just "their team's" — no team model exists) are still out of scope. Visits shipped in full (`GET /api/visits`, `GET /api/visits/{id}`, `POST /api/visits`, with FK-constrained `ClientId`/`LocationId` and the accepted-visit concurrency check on both create and accept). Clients & locations shipped (`GET`/`POST /api/clients`, `PATCH /api/clients/{id}` to edit a client's details, `POST /api/clients/{id}/locations` to add a location to an existing client — both `ClientManager`-only — per-client visit-count stats, Supervisor scoped to their `AssignedLocationId`); deleting a `Client`/`Location`, editing an existing `Location`, and changing a Supervisor's `AssignedLocationId` after user creation are still out of scope. Dashboards & stats have shipped (`GET /api/statistics/employees/{id}/monthly`, `GET /api/statistics/status`, `GET /api/statistics/clients/most-visited`, `GET /api/statistics/supervisors`) built entirely on existing data — no new entity or migration. Leave requests have shipped in full (`POST`/`GET`/`PATCH`/`DELETE /api/leaves`, `PATCH /api/leaves/{id}/accept|reject|request-delay` with rank-based approver routing); no leave-balance/accrual tracking exists, and re-actioning a `DelayRequested` request isn't supported (it's a terminal status — see `.squad/plans/leaves/07-story-leave-requests-and-approval-workflow.md` Edge Cases). The per-employee monthly rollup still omits "Leaves" — `leaves` has shipped, but integrating its data into `StatisticsEndpoints.GetEmployeeMonthlyActivityAsync` is an explicitly deferred follow-up to the `dashboards` feature, not part of the `leaves` story; there is no attendance *history* table anywhere (`Employee.AttendanceStatus` is a single current-value column, so the monthly rollup reports today's status plus a derived proxy, not "status during that month"); and a Supervisor's "team" for dashboards purposes is a heuristic (visit assignments under the Supervisor's assigned client), not a real reporting hierarchy — same gap as the task/visit "sees all" superset above, just scoped differently because Admin/Manager explicitly need a per-team breakdown. Notifications have shipped in full: storage, self-service reading (entity, `GET`/`PATCH .../read`), and every trigger — leave submission/accept/reject/request-delay, plus task and visit assignment — is wired (`NotificationType` has six members, not the original one) — see `.squad/plans/notifications/07-story-leave-request-notifications.md`'s Addendum. No per-notification-type user preferences and no real-time push (still 30s client-side polling) exist; these were never asked for.
